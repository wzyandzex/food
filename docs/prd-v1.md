> 状态：v1.1 已吸收五项产品决策（2026-08-23）· 前版：v1.0 草案

## 1. 产品概述与定位

**一句话定位**：一款手机优先的「做饭全记录」应用——找菜谱、记做饭、让别人点菜，把"今天吃什么"变成一段可回溯的共同记忆。

**产品名（拟定）**：「**开饭**」（KaiFan）。两个字、日常高频口语，寓意恰好覆盖产品闭环——别人点单、我下厨、菜上桌喊一声「开饭」；像"微信"成为动作本身一样，"今晚开饭"天然是产品的口头传播语。视觉意象：一碗冒着热气的米饭。备选：「小灶」（"开小灶"的亲昵感）、「一顿」（呼应以顿为核心单位的模型）、「灶记」（记录感最强）。

**用户画像**

| 人群 | 核心诉求 | 对应功能 |
|---|---|---|
| 情侣 / 夫妻 / 家庭 | "今天吃什么"的协商成本高 | 点单、排餐计划 |
| 单身独居做饭人 | 记录生活、不想每天想菜单 | 做饭日志、推荐 |
| 健身 / 饮食管理 | 控制摄入、复盘饮食 | 营养字段、统计看板 |
| 家庭主厨 / 主妇 | 多人吃饭、采购繁琐 | 多人点单合并、购物清单 |
| 厨艺初学者 | 不知道做什么、怎么做 | 菜谱市场、难度/时长筛选 |

**设计原则**
1. 移动优先：一切交互按单手竖屏设计。
2. 免登录优先：浏览、点单等单向操作不强制注册（渐进式注册，见 §4.1）。
3. 以「顿」为核心单位：一顿饭 = 多个菜的集合，记录、点单、采购都围绕"顿"聚合（见 §7，这是最容易漏掉的建模前提）。
4. 记录默认私密：做饭日志默认仅自己可见，分享是显式动作。
5. 零现金成本：不购买任何付费服务（无公众号认证、无 Apple 开发者账号、无付费云）；规模为发起人及亲友圈（其他人各自携带其亲友使用），一切选型按免费额度设计。

## 2. 平台策略：iOS 免 App Store 安装可行性评估

**结论先行：可以绕过，推荐路线是 PWA（添加到主屏幕），而不是侧载。** 理由与各路径对比如下。

| 路径 | 成本 | 限制 | 适用性 |
|---|---|---|---|
| **PWA（添加到主屏幕）** ✅ | 0（就是 Web 应用本身） | 见下方能力清单 | **唯一适合面向普通用户规模化分发的免审路径** |
| Apple 免费账号侧载（Xcode / AltStore / SideStore） | 0 | 签名 7 天过期，需定期连电脑或同 Wi-Fi 重签 | 仅限自己和极客，不可分发 |
| Ad Hoc 分发 | $99/年 | 需逐台收集用户 UDID，年度上限 100 台，用户操作门槛极高 | 封闭小圈子内测勉强可用，不推荐 |
| 企业证书 In-House | $299/年 | 苹果严查"非企业内部使用"，随时吊销，连带封号 | 高风险，禁止纳入方案 |
| TestFlight | $99/年 | 仍需过 Apple Beta 审核，构建 90 天过期需循环邀请 | 属于"官方旁路"，可作为未来内测渠道，不算绕过 |
| TrollStore 等系统漏洞永久签名 | 低 | 仅覆盖 iOS 14.0–16.6.1 / 17.0 部分版本，随系统更新失效 | 不可依赖 |

**PWA 在 iOS 上的能力核对（针对本项目需求逐项确认）**

| 需求交互 | iOS PWA 支持情况 |
|---|---|
| 全屏独立窗口、桌面图标、启动画面 | ✅ manifest + standalone（iOS 11.3+） |
| 离线缓存已浏览菜谱 | ✅ Service Worker |
| 拍照 / 相册上传菜品图 | ✅ `<input type=file capture>` 与 getUserMedia |
| 语音提问搜菜谱 | ⚠️ 部分：WebKit SpeechRecognition（iOS 14.5+）依赖" Siri 与听写"权限且稳定性一般；**降级链路**：系统键盘自带听写按钮（所有输入框原生可用）→ 录音上传 + 服务端 ASR（见 §9）。注意：微信内置浏览器里录音受限，但点单方只需点选不需语音，不受影响 |
| 推送通知（点单到达提醒） | ✅ iOS/iPadOS 16.4+，但**要求用户先添加到主屏幕**；更早系统降级为公众号模板消息/短信 |
| 本地存储 | ⚠️ Safari 浏览器标签内存储受 ITP 7 天清理限制；添加到主屏幕后的 PWA 不受限。策略：后端为准，本地仅作草稿缓存 |

**长期路线**：业务代码保持纯 Web。若日后确需原生能力（小组件、手表、更强推送），用 Capacitor 把同一套代码包成原生壳，走 TestFlight 内测 → App Store 上架，复用率 ~95%，前期投入零浪费。

## 4. 核心模块详述

### 4.1 账户与身份（新增，原需求缺失）

- **登录方式（零成本方案）**：邀请码注册 + 用户名密码，邮箱验证码/魔法链接用于找回（Supabase Auth 内置，免费）。短信登录废弃（每条短信都产生费用）；微信授权登录放弃（需认证公众号 300 元/年）。邀请码在亲友圈场景下一石二鸟：既是准入控制也是传播机制（老带新），注册开关可配置（默认邀请码制，可切开放开注册）。
- **渐进式注册**：浏览菜谱完全免登录；点单链接免登录可选菜（留昵称即可）；当用户产生"留存型"行为（收藏、记录做饭、发起点单）时才引导注册，并把此前的匿名点单记录合并进正式账号。
- **忌口 / 过敏原档案**（新增，健康安全关键项）：用户维护自己的忌口与过敏原，点单时自动随单携带，发起人汇总时高亮冲突。

### 4.2 菜谱市场

**数据来源：多渠道导入管线（全部在管理端操作，见 §4.7）**

> 合规基调随定位调整：本项目非商用、亲友圈规模，不再追求"全面采集"。单篇 URL 导入并保留来源署名属合理范畴；仍禁止批量爬取竞品整库（违反其用户协议，且有判例风险）。

统一入口是 **菜谱 JSON Schema**（`recipe.v1`：标题、成品图、份量、难度、时长、标签、食材表[名称·用量·单位·可选]、步骤数组、营养估算、来源类型与来源地址）。所有渠道最终都归一到这个格式：

1. **手动录入**：管理端表单，兜底渠道。
2. **JSON / XLSX 批量上传**：粘贴或上传文件（提供模板），先校验出报告（错误行清单）再入库。
3. **URL 单篇导入**：粘贴任意菜谱页链接 → 服务端抓取正文 → 大模型抽取为 Schema → 人工核对后入库，自动写入 `source_url` 署名。
4. **大模型调研生成**：给定菜名清单（如"川菜家常 30 道"），LLM 逐道生成结构化菜谱，人工抽检后入库；AI 生成内容显著标注。
5. **图片/OCR 导入**（增强）：手写菜谱或书本拍照 → 视觉模型转 Schema。
6. **开放数据源**：TheMealDB 等 CC 授权库脚本化翻译入库，冷启动补充。

所有渠道共用「暂存 → 校验报告 → 人工确认 → 入库」两段式流程，坏数据不直接进公共库；支持反向导出为 JSON，数据永远可带走。

**功能明细**
- 检索：菜名 / 食材 / 标签（难度、时长、荤素、减脂、下奶……）多维度；语音输入经 ASR 转文字后走同一检索管道（v1 仅做"语音→关键词"，"家里有鸡蛋和西红柿能做什么"这类问句理解放 v2，作为差异化亮点）。
- 详情页：成品图、食材表（含用量、可勾选"家里有"）、分步骤做法（可勾进度）、营养估算（选填字段，服务健身人群）、来源与作者署名。
- 收藏夹、自建菜谱、**改编（fork）**：从已有菜谱派生修改版并保留溯源署名。

### 4.3 做饭记录

- **今日要做**：首页聚合三个来源——排餐计划、他人点单结果、自己随手添加。
- **记录粒度 = 顿**：一次记录包含日期 + 餐次（早/午/晚/夜宵）+ 多个菜 + 参与人（谁吃了，v2）。
- 每个菜可关联市场菜谱（引用而非复制，菜谱更新不破坏历史），也允许无菜谱的自由记录。
- 完成后上传成品照片（多张）、打分、写一句复盘（"盐少了，下次 1.5 倍"）——复盘是提升复做质量的关键钩子。
- 日志时间线：按天/周/月浏览的照片流；空态引导"今天做了什么？"。
- 统计看板（P1）：本月做了几顿、最常做的菜 Top10、新菜尝试数、连续做饭天数——天然的朋友圈分享素材（带水印海报，增长钩子）。

### 4.4 点单模块（含分享方式决策）

**三种分享方式对比与建议**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 内置好友体系 | 关系稳固、体验连贯 | 冷启动难（双边网络效应），MVP 阶段 ROI 低 |
| B. 分享链接免登录 | 微信转发零摩擦，长辈也会用 | 无身份沉淀，历史记录只能显示昵称 |
| C. 必须进 App | 数据完整 | 摩擦最大，转化率最低 |

**建议：B 为主，叠加"渐进式身份锚定"**——点单人免登录即可选菜并留昵称；提交后温和引导"绑定手机号/微信，下次不用再填"，绑定后双方历史自动归并。A 作为 P2 的"饭搭子群"（2–10 人小圈子，非全量好友图谱）演进，C 不采用。

**发起人流程**
1. 选择点单场景（今晚 / 周末聚餐），从收藏、历史、推荐中挑 10–30 道候选菜（或允许"任意点"，见边界场景）；
2. 设置：截止时间（默认当天 17:00）、每人可点菜数、是否允许自由报菜名、每人份量；
3. 生成点单链接 `https://host/o/{token}`，微信转发。

**点单人流程（全程免登录）**
1. 打开链接 → 菜单卡片流（图、名、简介、难度、时长）；
2. 选菜 + 份数 + 备注（忌口自动带入，可临时增改）；首次提交后提示留联系方式；
3. 截止前可自行修改；截止或发起人关单后锁定。

**结果回流**
- 发起人收到通知，查看汇总视图：谁点了什么、按菜聚合的份数、忌口冲突高亮；
- 一键生成**采购清单**：Σ(菜谱食材 × 份数)，手动剔除"家里已有"，剩余即为**缺失食材清单**，可一键回发给对应点单人（微信转发文本/图片，v1 不要求点单人侧 App 内接收）；
- 这顿做完后，CookLog 自动关联该点单会话，形成双向记录（见 4.5）。

**实现要点**
- token 为 128bit 随机串，绑定会话、默认 72h 有效、可续期/撤销；"知道链接即可点单"本身即预期语义，泄露风险可接受，配合提交次数限制防刷；
- 提交幂等：`(orderSessionId, 提交者标识)` 覆盖式更新；
- 微信内打开为纯 H5，无额外依赖。卡片式分享需要认证公众号 JS-SDK（300 元/年），**已决策放弃**：普通链接在微信内的预览兜底，观感通过 Open Graph 标签优化。

### 4.5 点单记录（双维度）

- **我发起的点单**：每条 = 点单会话（谁点了什么、状态流转：进行中→已截单→已做饭/已取消）。
- **我参与的点单**：我通过别人的链接点过的所有菜及当前状态（对方还没做/已做）。
- 状态机：`进行中 → 已截单 → 采购中 → 已完成 / 已取消`，任一状态变化通知相关方。
- 隐私：参与记录中，对方的昵称与菜品可见，联系方式互不可见，沟通经由"缺失食材清单"等结构化消息完成。

### 4.6 补充模块清单（均为原需求缺失项）

| 模块 | 说明 | 优先级 |
|---|---|---|
| 食材与购物清单 | 菜谱→食材自动汇总合并；"缺失食材清单"本质是它的子集，应做成一等模块 | **P0（点单闭环依赖它）** |
| 通知中心 | 点单到达、截单提醒、状态变化；通道为 PWA Push（iOS 16.4+ 且已添加主屏）+ 站内未读红点；公众号模板消息因费用弃用 | P1 |
| 忌口过敏原档案 | 见 §4.1 | P0 |
| 统计看板 | 见 §4.3 | P1 |
| 排餐计划 | 本周日历，拖拽安排每顿吃什么；是"点单结果"与"做饭记录"间的调度枢纽 | P2 |
| 饭搭子群 | 2–10 人固定小圈子（情侣/家庭），圈内点单免转发链接 | P2 |
| 按食材搜索（清冰箱模式） | "我有鸡蛋、番茄、青椒能做什么"——核心差异化亮点 | P2 |
| 管理端（独立应用） | 见 §4.7：六渠道菜谱导入管线、内容审核、举报处理、邀请码与数据管理 | **P0（导入菜谱依赖它）** |
| 数据导出与注销 | PIPL 要求 | P1 |

### 4.7 管理端（独立应用，与用户端分离）

**为什么分离**：管理端面向运营者（你自己），交互密度高、无移动端诉求、绝不能暴露给普通用户；用户端面向亲友，只做消费与记录。二者分开开发、分开部署、分别设防。

- **形态**：同一仓库 monorepo 下的独立 Next.js 应用——`apps/web` 用户端、`apps/admin` 管理端、`packages/shared` 共享类型与 `recipe.v1` Schema 校验；作为两个独立的 Vercel 项目部署到不同域名。
- **访问控制**：无公开注册；管理员账号由种子脚本创建；中间件强制登录 + 管理员角色校验；开启 Vercel Deployment Protection 双保险。
- **功能清单**：
  1. 菜谱管理：六渠道导入管线（§4.2）、编辑、上下架、标签与分类维护；
  2. 内容审核：UGC 菜谱与举报处理；
  3. 用户管理：邀请码生成与吊销、封禁、数据导出；
  4. 运营数据：菜谱浏览量、点单转化、存储用量监控（盯紧免费额度）；
  5. 数据工具：Schema 校验器、批量导出 JSON、AI 生成任务队列。

## 5. 关键用户流程

**F1 新用户激活**：落地页（示例菜谱流，免登录可逛）→ 搜索/点击一道菜 → 收藏或"今晚就做"时触发注册 → 输入邀请码 + 设置账号密码 → 回到原操作（不丢失上下文）。

**F2 找菜谱**：首页搜索框 → 键盘听写/麦克风按钮 → ASR → 关键词结果流 → 详情页 → 「加入今日要做」或「收藏」。

**F3 做饭记录**：首页"今日要做" → 开做（步骤可勾进度、可计时）→ 完成 → 拍照 → 打分 + 一句话复盘 → 写入日志；断网时存本地草稿，联网自动同步。

**F4 点单（发起人）**：点单 Tab → 新建点单 → 选候选菜 + 设规则 → 生成链接 → 微信转发 → 收到点单通知 → 查看汇总 → 生成采购清单 → 勾掉已有 → 把缺失清单发回点单人 → 做饭 → 记录自动关联。

**F5 点单（参与者）**：微信里打开链接 → 浏览菜单 → 选菜 + 份数 + 忌口 → 提交（留昵称，可选绑定手机）→ 截止前可改 → 之后在自己"我点的单"里看到状态（若绑定了身份）。

## 6. 边界场景与异常处理

| # | 场景 | 处理 |
|---|---|---|
| 1 | 链接过期 / 被发起人关闭 | 友好提示页 + "让 TA 重新分享"引导文案 |
| 2 | 点单人重复提交 | 截止前覆盖式修改；截止后锁定只读 |
| 3 | 多人点同一道菜 | 按菜聚合份数；食材按份数倍乘后同名合并（v1 单位不换算，同名相加） |
| 4 | 点单人报了库里没有的菜（自由点单） | 进入"待补菜谱"队列：发起人可手写做法、忽略，或触发 AI 生成参考做法（标注为 AI 内容） |
| 5 | 所点菜品含发起人过敏原 | 汇总页红色高亮 + 明确警示 |
| 6 | 点单人未留任何身份就关页 | 记录以"微信用户/昵称"存在，发起人仍能看到点了什么；引导语在提交成功页 |
| 7 | 照片上传失败 / 弱网 | 本地草稿暂存 + 后台静默重试；记录先落库后补图 |
| 8 | 离线使用 | 已浏览菜谱 SW 缓存可看；新建记录排队待同步，冲突以时间戳 newer-wins |
| 9 | 语音识别失败/为空 | 降级到文字框 + 热门推荐占位，明确告知"没听清" |
| 10 | 发起人取消这顿饭 | 状态置"已取消"并通知所有点单人 |
| 11 | 账号注销 | 该用户匿名化；其在他人点单中的痕迹保留昵称脱敏展示（保护对方历史完整性） |
| 12 | 同一用户多设备 | 服务端为准 + 登录互踢策略（v1 允许共存，记录以服务端合并） |
| 13 | 深夜跨天点单（23:50 点"今晚"） | "顿"归属按发起人设定的餐次而非提交时刻 |
| 14 | 菜谱被作者删除/下架 | 历史记录与点单中的引用转为快照（冗余存储名称与主图），不白屏 |

## 9. 技术架构建议（简要）

- **仓库结构（monorepo）**：`apps/web` 用户端 · `apps/admin` 管理端 · `packages/shared`（共享类型、`recipe.v1` Schema 与校验逻辑），必要时再拆 `apps/api`。
- **前端**：Next.js + TypeScript + Tailwind，PWA（Serwist），移动优先响应式；一套代码覆盖 Android/iOS/桌面。
- **后端与数据库（全免费额度）**：Supabase 免费档一站式（Postgres 500MB + Auth + Storage 1GB）；备选组合 Neon（免费 Postgres）+ Cloudflare R2（免费 10GB、零流出费）。照片在客户端压缩（≤1600px、WebP 约 200KB）后上传，1GB 可存约 5000 张；逼近上限前迁移 R2。
- **语音**：三级降级——Web Speech API（可用时零成本）→ 系统键盘听写 → MediaRecorder 录音上传 + 服务端 ASR（自托管 Whisper 或云厂商免费额度）；ASR 结果走统一检索管道。
- **认证**：邀请码 + 用户名密码 + 邮箱找回（Supabase Auth 内置，零成本）；短信与微信授权均因费用弃用。
- **部署（全免费平台）**：Vercel Hobby × 两个项目（用户端/管理端分域部署；Hobby 条款本就限定非商用，与本产品定位一致）。国内直连 Vercel 时快时慢，亲友内测可接受；若不稳则平移 Cloudflare Pages（同样免费）。自定义域名约 $10/年，暂不购买，先用 `kaifan.vercel.app` 类免费子域名。GitHub Pages 仅支持纯静态站点，本项目有数据库与登录，不适用。

## 10. 合规与风险清单

| 风险 | 等级 | 对策 |
|---|---|---|
| 菜谱爬取的著作权 / 反不正当竞争风险 | **高** | 放弃爬取竞品库；改用开放数据 + AI 生产 + UGC 三管线（§4.2），AI 内容显著标注 |

## 11. 决策记录（2026-08-23）
